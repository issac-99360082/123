# 方向評估與選型（Opportunity Analysis）

本文件是專案規格第一階段的產出：在寫任何程式碼之前，先比較多個可行方向，
建立評分模型，選出綜合分數最高的一個。

## 1. 硬性限制（來自規格）

依優先順序：

1. 實際可產生收入的可能性
2. 能高度自動化運作
3. 初始資本需求低
4. 維護成本低
5. 能由單一開發者部署與管理
6. 不依賴違法、欺騙、垃圾訊息或侵犯第三方服務條款的方法

第 6 點是**淘汰條件（knockout criterion）**，不是評分項目：任何需要爬取禁止爬取的
內容、規避付費牆、大量未經同意的訊息推送、或違反第三方 API 條款的方向，
無論分數多高一律排除。

## 2. 評分模型

六個維度，1–10 分，10 分最有利。標示「(反向)」者代表「越低越好 → 分數越高」
（例如啟動成本 10 分 = 幾乎零成本）。

| 維度 | 權重 | 說明 |
|---|---|---|
| 預期收入能力 | 25% | 可觸及的付費客群規模 × 可持續的客單價 |
| 競爭程度（反向） | 15% | 是否存在可被單一開發者佔據的縫隙 |
| 開發難度（反向） | 15% | 單人在數天內能否做出可收費的 MVP |
| 啟動成本（反向） | 15% | 第一個月的現金支出 |
| 自動化程度 | 15% | 無人值守運作、無需人工交付的比例 |
| 首筆收入難度（反向） | 15% | 從部署到第一張訂單的摩擦 |

加權總分 = Σ(分數 × 權重)。

## 3. 候選方向

### A. 垂直型 SaaS（特定產業工作流工具）
針對單一產業（如診所、健身房、律所）的排程／客戶管理系統。

### B. 開發者 API 服務（用量計費）
把某個技術能力包成 API 按呼叫計費（如文件轉檔、擷取、驗證）。

### C. 自動化 Bot（Discord / Telegram / Slack）
社群或工作流機器人，訂閱制。

### D. 資料監控／通知服務
持續監看外部資料源（網頁、API、端點），變化時以結構化方式通知。

### E. 數位工具（一次性買斷的網頁工具）
單次付費的線上工具或模板。

### F. 運算資源收益（GPU 出租／挖礦／渲染農場）
以硬體換取收入。

### G. 合法的市場中性金融工具
資金費率套利、跨所價差等中性策略工具。

## 4. 評分結果

| 方向 | 收入能力 (25%) | 競爭↓ (15%) | 開發難度↓ (15%) | 啟動成本↓ (15%) | 自動化 (15%) | 首筆收入↓ (15%) | **加權總分** |
|---|---|---|---|---|---|---|---|
| A. 垂直 SaaS | 8 | 6 | 4 | 8 | 6 | 3 | **6.05** |
| B. 開發者 API | 7 | 4 | 6 | 8 | 9 | 6 | **6.70** |
| C. 自動化 Bot | 5 | 5 | 7 | 9 | 8 | 5 | **6.35** |
| **D. 資料監控／通知** | **8** | **6** | **7** | **9** | **10** | **7** | **7.85** |
| E. 數位工具（買斷） | 4 | 3 | 8 | 9 | 7 | 7 | **6.10** |
| F. 運算資源收益 | 6 | 7 | 6 | 1 | 9 | 8 | **6.15** |
| G. 市場中性金融 | 9 | 5 | 3 | 2 | 8 | 6 | **5.85** |

### 各項評分理由（重點）

**A. 垂直 SaaS — 6.05**
收入能力高（B2B 客單價可到 $100+/月），但銷售是人力密集的：需要 demo、
導入、資料遷移。首筆收入難度 3 分是致命傷 —— 與「高度自動化」「單人管理」相衝突。

**B. 開發者 API — 6.70**
自動化程度極高、開發者願意自助刷卡。但通用型 API（轉檔、OCR、擷取）競爭極度激烈，
且多半是與大廠的成本戰，定價權低（競爭 4 分）。

**C. 自動化 Bot — 6.35**
開發快、成本低，但平台風險高（依附於 Discord/Telegram 政策），
且免費替代品極多，付費轉換率低（收入能力 5 分）。

**D. 資料監控／通知 — 7.85（勝出）**
- **收入能力 8**：買方是企業而非個人。競品定價（Visualping、UptimeRobot、
  ChangeTower 等）落在 $15–$100/月，證明市場願付。監看的是「錯過就有損失」
  的資訊：對手降價、法規頁面更新、供應商條款變更、API changelog。
- **競爭 6**：既有工具多為「給人看的截圖／視覺 diff」。**開發者導向、
  webhook-first、輸出結構化 JSON diff** 的縫隙仍在，且正在被 AI agent 
  工作流放大（agent 需要的是機器可讀的變更事件，不是紅框截圖）。
- **開發難度 7**：核心迴圈（抓取 → 擷取 → 雜湊比對 → 通知）明確且封閉，
  單人數天可完成可收費版本。
- **啟動成本 9**：一台 $5–$12/月的 VPS 起步，無需 GPU、無需庫存、無需牌照。
- **自動化 10**：純無人值守。使用者自助註冊 → 自助刷卡 → 系統自動排程執行。
  沒有任何一筆收入需要人工介入交付。
- **首筆收入難度 7**：免費方案可即刻證明價值（第一封變更通知就是價值展示），
  升級路徑自然（要更短的檢查間隔、更多監控項就付費）。

**E. 數位工具（買斷）— 6.10**
無經常性收入，每個月都要重新獲客，LTV 低。

**F. 運算資源收益 — 6.15**
啟動成本 1 分即出局：需要實體硬體與電力，且毛利受幣價／市場價格支配，
不是軟體專案能控制的變數。

**G. 市場中性金融 — 5.85**
收入上限最高，但啟動成本需要自有本金、開發難度高（風控、對帳、故障即虧損），
且在多數司法管轄區「代客操作」需要牌照。以「合規、低資本、單人維護」的
限制來看不可行。

## 5. 決策

**選定：D. 資料監控／通知服務**，加權總分 **7.85**（次高者 B 為 6.70）。

具體產品定位（收斂到可執行的範圍）：

> **Watchpost** — 開發者導向的網頁／API 變更監控服務。
> 使用者宣告要監看的 URL 與擷取規則（CSS selector / regex / JSON path），
> 系統依方案排程抓取、正規化、比對，**只在內容真正變化時**送出
> 帶 HMAC 簽章的 webhook（或 email），payload 是結構化 JSON diff。

### 為什麼是這個切法而不是「再做一個 Visualping」

| | 既有視覺監控工具 | Watchpost |
|---|---|---|
| 輸出 | 截圖 / 視覺紅框 | 結構化 JSON diff |
| 觸發對象 | 人（收信後自己看） | 系統（webhook 進入既有工作流／agent） |
| 擷取精度 | 整頁或框選區域 | CSS selector / regex / JSON path，可只看價格數字 |
| 噪音處理 | 弱（廣告、時間戳都會觸發） | 正規化 + 忽略規則 + 擷取後才比對 |

### 合規邊界（對應淘汰條件第 6 點）

本服務**不**做以下任何一項，且以程式碼強制執行（見 `app/core/fetcher.py`）：

- 預設遵守目標站台的 `robots.txt`（`RESPECT_ROBOTS_TXT=true`）
- 明確的 User-Agent，含服務識別與聯絡網址，不偽裝成瀏覽器使用者
- 每網域最小抓取間隔，禁止高頻打擊目標站台
- 阻擋私有網段／metadata 端點（SSRF 防護），避免被當成內網掃描跳板
- 只抓取公開可存取的內容；不提供繞過付費牆或登入牆的功能
- 通知只送到使用者自己設定的 webhook / 自己驗證過的信箱，不做任何未經同意的推播
