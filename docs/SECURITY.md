# 安全模型與殘餘風險

本文件記錄「已知但尚未完全消除」的風險。它存在的理由是:
audit 中被修掉的問題會留下回歸測試,而**沒被完全修掉的問題必須被寫下來**,
否則下一個人會以為它不存在。

已修正並附回歸測試的項目見 `tests/test_security_regressions.py`。

---

## 威脅模型

Watchpost 的核心特性決定了它的風險輪廓:**它接受陌生人提供的 URL,
然後用我們的伺服器去抓取**。這使它天生是一個 SSRF 代理候選者,
也是一個運算資源的免費出租對象。

主要威脅來源:

| 來源 | 能做什麼 |
|---|---|
| 匿名網路使用者 | 註冊、耗用免費額度、探測公開端點 |
| 已註冊使用者 | 指定任意 URL、任意擷取規則、任意 webhook 目的地 |
| 被監控的網站 | 回傳惡意內容、超大內容、重導向、無限重導向 |
| 使用者的 webhook 接收端 | 慢速回應、佔用送信執行緒 |

## 殘餘風險

### R1. DNS rebinding(中)

**狀態:未完全消除。**

`validate_target_url()` 解析主機名並確認所有結果都是公開位址,
但**實際連線時 httpx 會再解析一次**。攻擊者若控制權威 DNS 且 TTL 極短,
可以在這兩次解析之間把記錄改成 `169.254.169.254`。

已降低的部分:每一次重導向都會重新驗證(見 audit_1 / C1),
所以最常見的 SSRF 路徑已封閉。

**真正的緩解在網路層,不在應用層**:

- 於防火牆/安全群組封鎖 worker 對 RFC1918、`169.254.0.0/16` 的出站連線
- 雲端環境強制 IMDSv2 並將 hop limit 設為 1
- 或讓所有出站抓取走一台只允許公開網段的 egress proxy

**部署前務必至少做到第一項。** 應用層的檢查是縱深防禦,不是唯一防線。

### R1b. 反向代理設定錯誤會使所有 per-IP 控制失效(中)

**狀態:已加上開關,但正確性取決於部署。**

`TRUST_PROXY_HEADERS` 預設為 `false`。若你把它設為 `true`,
**前面就必須有一台會覆寫 `X-Forwarded-For` 的反向代理**。
否則使用者可以自行指定該標頭,等於自己挑選 rate-limit 的分桶。

audit_2 實測:標頭被無條件信任時,單一攻擊者在限制為 5 的情況下成功建立 **20/20** 個帳號。

Caddy 與 nginx 的預設 `reverse_proxy` / `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for`
行為都是**附加**而非覆寫。請確認你的代理是覆寫,或改用只信任最後一跳的設定。

### R2. 帳號列舉(中)

**狀態:已縮小,未關閉。**

註冊時的錯誤訊息已改為不揭露「該信箱是否已註冊」,
但**HTTP 狀態碼仍不同**(已存在 → 400,新帳號 → 201)。

要完全關閉,需要改成 email 驗證流程:無論信箱是否存在都回傳相同的 202
(「請至信箱收信」),真正的區別只出現在信件中。這需要 SMTP,
因此列為待辦而非已完成。

### R3. 沒有 email 驗證(中)

**狀態:已緩解,未消除。**

註冊已限制為每 IP 每小時 5 個帳號(`SIGNUP_LIMIT_PER_HOUR_PER_IP`),
但擁有大量 IP 的攻擊者仍可批量開免費帳號,每個帶 3 個監控額度。

上線前建議至少加上其一:
- email 驗證(未驗證前不排程任何檢查)
- 註冊時的 CAPTCHA
- 免費方案要求綁定信用卡(Stripe 可只驗證不扣款)

**目前的免費方案成本上限**:每帳號 3 個監控 × 每小時 1 次 ≈ 2,160 次檢查/月。
以單機 500 萬次/月的保守容量計,約 2,300 個濫用帳號才會吃滿一台機器。

### R4. 速率限制是單一程序內的記憶體狀態(中)

`TokenBucket` 與 `SlidingWindow` 都存在程序記憶體中。因此:

- 跑 N 個 API 副本時,實際限制變成 N 倍
- **API 重啟會清空所有計數**,包含登入鎖定

單一 API 程序(絕大多數部署)行為正確。水平擴充時必須換成 Redis 後端。

### R5. 使用者的 request_headers 以明文存放(中)

使用者監控自己的 API 時會填入 `Authorization` 標頭,這些憑證以明文存在
`monitors.request_headers`。API 回應不會回傳它們,但:

- 資料庫備份含有這些憑證
- 有資料庫讀取權限的人可以看到

緩解:加密該欄位(需金鑰管理),或在文件中明確告知使用者只放唯讀憑證。
**目前採後者**,並已寫入 `privacy.md`。

### R6. 內部位址在錯誤訊息中被回報(低)

`Target 10.1.2.3 is not a public address.` 會告訴使用者某個位址被判定為私有。
這對內網探測的幫助有限(判定純粹依 IP 區段,不代表該主機存在),
但仍是不必要的資訊。

### R8. 送信與檢查共用同一個執行緒池(低)

`tick()` 先跑檢查、再跑送信,兩者都用 `WORKER_CONCURRENCY`。
送信已改為併發(audit_2 / H3),但兩者仍在同一個 tick 內序列執行。
在極端負載下,大量送信會延後下一輪檢查。

監控方式:`/metrics` 的 `monitors_due` 與 `deliveries_pending` 同時上升。

### R7. 單點故障(中)

單一 worker 程序擁有整個排程。它掛掉時**檢查會靜默停止**,
API 仍然正常回應,`/healthz` 也仍然回 200。

緩解:監控 `/metrics` 的 `monitors_due`,持續上升即代表 worker 沒在工作。
建議設一條外部告警。

## 已驗證有效的防護

以下項目在 audit 中被實際攻擊過並確認擋住:

| 防護 | 驗證方式 |
|---|---|
| 重導向 SSRF | 公開主機 302 → 127.0.0.1,已擋(`blocked_target`) |
| 無限重導向 | 重導向迴圈,已擋(`too_many_redirects`) |
| gzip 解壓縮炸彈 | 300 MB 展開內容,串流上限在 2 MB 處截斷,記憶體有界 |
| ReDoS | `(a+)+$` 等 6 種病態模式,最壞 2.0s(修正前無上限) |
| 跨帳號資料存取 | 另一帳號讀/改/刪他人監控,全部 404 |
| Stripe 簽章偽造 | 偽造簽章被拒且不留下事件紀錄 |
| Stripe 重放 | 重複事件 id 被忽略 |
| 併發重複認領 | 4 worker × 40 監控,零重複 |
| X-Forwarded-For 偽造 | 預設不信任該標頭,20/20 → 0/20 |
| 登入鎖定被用於阻斷合法使用者 | 兩層鎖定;12 個攻擊來源後,擁有者仍可登入(200) |
| 重導向鏈時間放大 | 全域 deadline,超時即中止(`deadline_exceeded`) |
| 帳號刪除與資料匯出 | 實際刪除並級聯至 monitors/checks/change_events/api_keys |
| 保留期限 | 逾期的 check 與 change_event 實際被刪除 |
